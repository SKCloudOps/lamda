📋 Quick Reference (2-3 min answers)

Pod Identity vs IRSA

Both provide temporary credentials to pods without embedding access keys. IRSA uses OIDC + STS web identity federation; Pod Identity uses a mutating webhook + Agent on each node. For new EKS clusters, Pod Identity is simpler operationally. Choose IRSA if the cluster already uses it, if you're using older add-ons, or if security team hasn't cleared Pod Identity yet.
AWS/EKS

IAM User vs IAM Role

IAM Users are long-lived identities (typically for people); IAM Roles are temporary (for services and cross-account access). For any cloud-native architecture—Kubernetes, Lambda, EC2—use roles, not users. Roles enforce automatic credential rotation and limit blast radius on compromise. Users are historical; roles are the security default.
Security/IAM

Branching & Hotfix Strategy

Use trunk-based development (short-lived feature branches, max 1-2 days). For hotfixes: branch off main, fix, create new immutable artifact (v1.2.1), deploy to staging for smoke tests, then prod. Merge hotfix back to main without rebasing; develop picks it up automatically. Immutable artifacts ensure every re-deploy is identical. Never rebuild the same version.
CI/CD/DevOps

Lambda Sync vs Async

Synchronous: caller waits for result (APIs, validation). Asynchronous: caller gets 202 immediately; Lambda runs in background (email, analytics). Async includes AWS retries (2x default) + DLQ for failures. Use sync for critical path; async for non-critical tasks. Async decouples caller from execution and has built-in fault tolerance.
AWS Lambda

Blue/Green vs Canary Deployment

Strategy choice follows state design, not vice versa. Key question: can old and new code share state safely? If yes (backward-compatible schema), canary is safe. If no (breaking changes), use blue-green or feature flags. Don't choose strategy first; design state for compatibility, then deployment strategy becomes optional.

📖 Detailed Answers (Full Context)

Pod Identity vs IRSA (Deep Dive)

Both solve the same problem: Provide temporary AWS credentials to Kubernetes pods without embedding long-lived keys.

  • IRSA (IAM Roles for Service Accounts): Uses EKS OIDC provider + STS web identity federation. When pod tries to call AWS API, kubelet retrieves temporary credentials via STS AssumeRoleWithWebIdentity. Requires OIDC provider setup (one-time). More mature, widely used.
  • Pod Identity: Uses mutating webhook + Agent running on each node. Agent intercepts credential requests, provides temporary tokens from local cache. Simpler setup (2-3 CLI commands), lower latency (no external OIDC call), younger codebase.
  • Pod Identity adoption: Released Sept 2023, GA mid-2024. Many production clusters still on IRSA due to switching costs + add-on compatibility.
Interview positioning: "For new clusters without legacy constraints, Pod Identity is my first choice because it's simpler to operate. I'd choose IRSA if the cluster already uses it, if we're using older add-ons that require it, or if the security team hasn't yet certified Pod Identity."

Real gotchas: Pod Identity Agent must run on every node. Pod Identity associations are explicit (via annotation or Terraform). IRSA has more mature tooling for multi-account cross-account scenarios.

IAM User vs IAM Role (Philosophy & Practice)

The fundamental difference: Identity type and credential lifecycle.

  • IAM User: Long-lived identity, typically for a person. Creates access keys (ID + secret) or password. Credentials persist until manually rotated. Assumes role via console or credentials. No automatic expiration.
  • IAM Role: Temporary identity, assumed by a principal (person, service, or cross-account). Generates temporary credentials (access key + secret + session token). Token expires automatically (default 1 hour, configurable). No permanent secrets stored.

Why roles win in cloud-native: Automatic credential rotation (no manual management). Session token expires (lower blast radius if compromised). Better audit trail (each session logged). Perfect for services (EC2, Lambda, ECS, pods).

When to use users: Legacy systems needing long-lived keys. Local AWS CLI testing (though federated identity is better). Almost never in production services.

Security story: "If a role is compromised, the attacker has credentials valid for ~1 hour. If a user's access key is compromised, the attacker has credentials valid indefinitely until rotated. This is why roles are mandatory for production services."

Real-world pattern: Developer uses federated identity (SAML/OIDC) to assume a role; gets temporary credentials valid for 8 hours. Application uses Pod Identity or EC2 instance profile; gets temporary credentials valid for 1 hour, auto-refreshed. No long-lived keys anywhere.

Branching & Hotfix Strategy (Complete Pattern)

The challenge: How to deploy hotfixes fast without corrupting main branch or destabilizing ongoing work?

Trunk-based development (recommended):

  • Developers work on short-lived branches (max 1-2 days)
  • PR → review → merge to main → CI/CD deploy to staging
  • No long-lived branches cluttering the history

Hotfix flow:

  • Create hotfix/bug-name branch off main
  • Fix code, commit, push
  • CI builds artifact with new version tag (v1.2.1)
  • Deploy to staging for smoke tests (5 minutes)
  • Manual approval → deploy to production
  • Merge hotfix back to main (no rebase; clean history)
  • Next release (v1.3.0) already includes the hotfix automatically

With immutable artifacts: v1.2.1 is a fixed version. If you re-deploy v1.2.1 six months from now, you get the exact same binary (same image digest, no rebuilding).

Why this beats Git Flow: No release branches getting stale. No cherry-picks causing merge conflicts. Hotfix automatically flows to all branches. Total time to production: 15 minutes.

Anti-pattern to avoid: "We have separate develop/main branches and cherry-pick hotfixes." This creates history nightmares, merge conflicts, and is slow (multiple PRs per fix).

Lambda Sync vs Async (Architectural Thinking)

The trade-off: Blocking caller vs. decoupling services.

Synchronous (API Gateway → Lambda):

  • Caller waits for result (user submits form, waits for response)
  • Caller's network connection stays open for entire duration
  • If Lambda crashes, caller sees error immediately
  • Retry logic is caller's responsibility
  • Timeout: 15 minutes max (but API Gateway times out at 29 seconds, so practical limit is ~25 seconds)

Asynchronous (SNS/SQS → Lambda):

  • Caller invokes Lambda, immediately gets 202 Accepted, disconnects
  • Lambda executes in background at its own pace
  • AWS automatically retries on failure (default 2 retries)
  • Dead Letter Queue catches persistent failures
  • Caller never sees execution result (must check via separate polling or webhook)

Cost implications: Sync ties up caller's network resources (connection pooling, SDK overhead). Async is cheaper (caller disconnects immediately) but requires DLQ monitoring.

Real scenarios:

  • Payment processing: Charge card is sync (user needs immediate confirmation). Send receipt email is async (user already has confirmation).
  • Image upload: Accept upload is sync. Resize image is async (user doesn't wait 10 seconds).
  • Database query: API call is sync. Analytics logging is async.
Gotcha: Async doesn't mean "fire and forget." You must monitor the DLQ. If messages sit there for hours, you have a data consistency problem. Set up alerts on DLQ depth.

Blue/Green vs Canary Deployment (State-First Thinking)

The key insight: Deployment strategy is NOT a choice; it's a consequence of state design.

The naive approach: "Let's use canary deployment" → select the tool → deploy. This fails when old and new versions can't share state.

The right approach:

  • First: Ask: can v1 and v2 safely coexist? Can they share RDS, cache, message queues?
  • If yes (backward-compatible schema): Canary is safe. Deploy to 1% of traffic. Monitor. Gradually increase. Rollback if errors spike.
  • If no (breaking schema change): Blue-green or feature flags. Atomic cutover. No v1/v2 coexistence.
  • If unsure: Redesign the state BEFORE deploying. "Can I add this field as nullable?" "Can I make the new code handle both data formats?" "Can I use a feature flag?"

Data format example:

  • v1 stores user location as flat: {city: "NYC", state: "NY"}
  • v2 wants nested: {location: {city: "NYC", state: "NY"}}
  • v1 writes flat format, v2 tries location["city"] → KeyError
  • Fix: v2 reads BOTH formats, writes BOTH formats. After full rollout, clean up flat format.
Interview positioning: "Deployment strategy is determined by whether old and new versions can share state. Design state for compatibility, then the deployment strategy becomes optional."

DevOps Anti-Patterns (The Gotchas)

1. Manual infrastructure changes: Ops ssh's into prod, runs commands manually. No audit trail. Next terraform apply undoes it. State diverges.

Fix: All infrastructure through code. File a ticket → engineer codes it → PR review → CI/CD deploy.

2. Skipping CI part of CI/CD: No tests, linting, scanning. Code ships directly to prod.

Fix: Mandatory checks (tests pass, linting clean, SAST clean). Slow down delivery slightly; prevent 90% of incidents.

3. Secrets in git: Passwords committed, lost forever in history.

Fix: Use Secrets Manager. Reference in code. Pre-commit hooks to detect secrets.

4. No observability: Code deployed. No one checks if it's working. 2 hours later, customers complain.

Fix: Logs (debug issues), metrics (alert on problems), traces (identify bottlenecks).

5. Manual release processes: Runbooks, checklists, human steps. Someone skips step 5 under pressure → incident.

Fix: Automate everything. Tag → build → test → deploy. Zero human steps.

6. Big bang deployments: Update all 10 servers simultaneously. One bad deploy → full outage.

Fix: Blue-green or canary. One bad deploy → 1% outage, easy rollback.

7. In-place server updates: SSH in, install patches, pray it works next time.

Fix: Immutable infrastructure. Packer builds AMI. Terraform deploys it. Change = replace servers, never update.

8. Single points of failure: One database, one load balancer, one AZ.

Fix: Multi-AZ, read replicas, backup/restore, redundancy everywhere.

Shift-Left Security in CI/CD (Full Pipeline)

The principle: Catch defects as EARLY as possible. Developer's laptop is earlier than production.

Layer 0: Developer's laptop (pre-commit):

  • Run: lint, unit tests, secret scanning (gitleaks)
  • Speed: <30 seconds (or developers skip it)
  • Failure: commit is blocked

Layer 1: GitHub PR merge gate (5-10 minutes):

  • SAST (Semgrep): code vulnerabilities
  • Dependency scanning (Snyk): vulnerable packages
  • Secret scanning (gitleaks): hardcoded credentials
  • Failure: PR blocked, requires review and fix

Layer 2: Build step (10-15 minutes):

  • Container image scanning (Trivy): OS-level vulnerabilities
  • IaC scanning (tfsec): infrastructure misconfigurations (open SSH, no encryption, etc.)
  • Failure: build blocked

Layer 3: Staging (manual testing):

  • Integration tests (real database, cache, etc.)
  • Failure: not deployed to production

Layer 4: Production (monitoring):

  • Runtime scanning (continuous image scanning, GuardDuty)
  • Alert on anomalies

Goal: Catch 95%+ of issues before Layer 4. By the time code reaches production, it's been vetted 10+ times.

Cost: Pipeline adds ~7 minutes total. Worth it? One prevented production incident pays for a year of scanning tooling.

S3 Lifecycle Policies (Cost Optimization at Scale)

The problem: Logs stored in S3 Standard forever = expensive. After 30 days, logs are rarely accessed.

The solution: Lifecycle policies automatically move objects to cheaper storage as they age.

Example flow:

  • Days 0-30 (Standard): $0.023/GB. Recent logs, frequently accessed.
  • Days 30-90 (Standard-IA): $0.0125/GB. Older logs, rarely accessed. 45% cheaper.
  • Days 90-365 (Glacier Flexible): $0.004/GB. Archive logs, almost never accessed. 82% cheaper. 1-5 minute retrieval time.
  • Days 365+ (Glacier Deep Archive): $0.00099/GB. Compliance holds, 7-year retention. 12-hour retrieval. Cheapest option.
  • Day 2555 (7 years): Delete. Compliance requirement met.

Real math: 500 GB/month log ingest = 6 TB/year.

  • Standard only: 6 TB × 12 × $0.023 = $1,656/month
  • With lifecycle: First month Standard ($115), then rolling window of IA/Glacier = $200/month average
  • Savings: 88% = $1,456/month = $17,500/year

Gotchas:

  • Retrieval costs: Glacier Flexible charges $0.03 per GB retrieved. If you query old logs frequently, IA might be better.
  • Minimum object size: Objects <128 KB are inefficient to transition; just leave them in Standard.
  • Incomplete uploads: Add AbortIncompleteMultipartUpload rule to clean up orphaned upload parts (hidden cost leak).

Terraform Drift & Lifecycle (Infrastructure State Management)

The problem (Drift): Infrastructure reality diverges from Terraform code. Ops manually adds security group rule. Terraform doesn't know. terraform apply removes it.

Common drift causes:

  • Manual changes (ops ssh into console, tweaks config)
  • External tools (another IaC tool, AWS CLI scripts, ansible)
  • AWS service updates (AWS changes default values)
  • Team coordination failure (two teams modifying same resource)

Prevention:

  • Remote state (S3 + DynamoDB locking): prevents concurrent applies
  • terraform plan in CI: detects unexpected changes before apply
  • Nightly drift detection: Lambda runs terraform plan, alerts if divergence
  • Strong discipline: all changes go through code, no manual AWS console changes

Lifecycle meta-argument patterns:

  • prevent_destroy = true: Protect critical resources (database). terraform destroy fails.
  • ignore_changes = [tags]: Allow manual tagging without Terraform overwriting.
  • create_before_destroy = true: Zero-downtime updates. New resource created, traffic shifts, old one deleted.
  • replace_triggered_by = [dependency]: Cascade replacements (update base image → rebuild all servers).
Golden rule: State file is source of truth. Manual changes must sync to code within 24 hours or be rejected on next apply.

Terraform State Locking & Secrets Management (Security & Coordination)

State Locking Problem: Two engineers deploy simultaneously. Both read state, make changes, write back. One change lost. Infrastructure is inconsistent.

Solution: DynamoDB Locking

  • Engineer A runs terraform apply
  • Terraform creates lock entry in DynamoDB (table: terraform-locks, key: prod/state)
  • Engineer B tries to apply → blocked ("resource locked")
  • Engineer A's apply completes → lock released
  • Engineer B can now apply

Gotcha: Stuck locks If Engineer A's machine crashes, lock persists forever. Solution: Add TTL to locks (auto-release after 1 hour).

Secrets Management Problem: Terraform state contains passwords (RDS, API keys). If state is unencrypted or uncontrolled, secrets leak.

Solution (multi-layered):

  • Never hardcode secrets: Use Secrets Manager, reference via data source.
  • variable "db_password" { type = string; sensitive = true } prevents logging in plan output.
  • Encrypt state at rest: S3 bucket with KMS encryption. Even if S3 is breached, data is encrypted.
  • RBAC on state: IAM policy restricts S3/DynamoDB access to Terraform runner role only.
  • Audit logging: CloudTrail tracks who accessed state, when, from where.
  • Secret rotation: Secrets Manager rotates password automatically (90-day lifecycle). Applications read from Secrets Manager, not state.

Real-world setup: 10-minute backup window (state is backed up with versioning). If state lost, restore from S3 version or terraform import existing resources back into fresh state.

Kubernetes Diagnostics (The Pyramid)

Tier 1: Cluster Health

  • kubectl get nodes → Node status (Ready, NotReady, MemoryPressure)
  • kubectl top nodes → CPU/memory usage per node
  • Red flag: nodes in NotReady or memory pressure

Tier 2: Pod Status

  • kubectl get pods -o wide → Pod status, IP, node assignment
  • Statuses: Running (healthy), Pending (can't schedule), CrashLoopBackOff (keeps crashing)

Tier 3: Pod Details

  • kubectl describe pod <pod> → Events section shows scheduling failures, image pulls, probe failures
  • kubectl logs <pod> → App output (errors, exceptions, stack traces)
  • kubectl logs --previous → Logs from before crash (if pod restarted)
  • kubectl top pod <pod> → Actual CPU/memory usage vs limits

Tier 4: Network & Connectivity

  • kubectl get endpoints <svc> → Is pod registered with service? Empty = no healthy pods.
  • kubectl port-forward svc/<svc> 8080:8080 → Test local connectivity
  • kubectl debug pod <pod> → Inspect pod's network namespace, test DNS, TCP connectivity

Tier 5: Deep Dive

  • kubectl exec -it <pod> -- bash → Shell into pod, check processes, file permissions, environment
  • kubectl get events -n <ns> → Cluster timeline of all events

Real workflow: Pod in CrashLoopBackOff → describe (shows events) → logs (shows error) → check node (resources?) → exec (verify environment) → port-forward (test connectivity). 80% of issues resolved by Tier 3.

Karpenter (Dynamic Instance Provisioning)

The problem Karpenter solves: Manual node groups are static, expensive, and inefficient. 50-node cluster with 45% average utilization = wasted capacity.

How Karpenter works:

  • Pod is unschedulable (no node has capacity)
  • Karpenter controller detects it
  • Evaluates pod resource requests (2 CPU, 4Gi memory)
  • Queries EC2 for compatible instances: t3.medium, t3.large, m5.large, etc.
  • Scores by cost (cheapest first, prefers spot)
  • Provisions instance (45-60 seconds boot time)
  • Pod scheduled on new node

Consolidation (the magic): Every 30 seconds, Karpenter checks: can I pack pods tighter? If 10 pods on Node A can fit on Node B, Karpenter drains A and deletes it. This is where 40-60% savings come from.

Real cost impact: 50-node cluster with 20% idle capacity = 10 wasted nodes at $0.1/hour = $24/day = $720/month. Karpenter removes idle nodes automatically.

Gotchas:

  • Pod resource requests: Karpenter uses them to size instances. No requests = Karpenter guesses wrong. ALWAYS set requests.
  • Spot interruptions: Spot instances are 70% cheaper but can be interrupted. Use PodDisruptionBudgets for critical workloads.
  • Consolidation too aggressive: Pod keeps restarting due to consolidation. Solution: increase TTL after empty (don't consolidate immediately).
  • IAM permissions: Karpenter needs EC2FullAccess or scoped policy to launch instances.

Setup: Helm chart install (5 min) + define provisioners (5 min) + update deployments with resource requests (1-2 hours) = 10-week project overall.

Observability: Logs vs Metrics vs Traces (Full Integration)

The Three Pillars Answer Different Questions:

  • Metrics: "What's happening?" (aggregated, quantitative) → CPU 78%, error_rate 0.2%, latency_p99 245ms
  • Logs: "Why did it happen?" (detailed, sequential) → "Database connection timeout after 30s, user_id=12345"
  • Traces: "How did it happen?" (causality across services) → API Gateway 1ms → Auth 2ms → Database 300ms

Real incident example: Users report slow API.

  • Metrics alert fires: request_latency_p99 > 1 second. Dashboard shows CPU 45%, memory 50%. Healthy resources.
  • Logs reveal issue: "Database query SELECT * FROM users took 4500ms." No index on user_id.
  • Traces identify bottleneck: Sample trace shows Database span = 4500ms (vs. API Gateway 5ms, Auth 10ms).
  • Root cause: Missing database index. Fix: CREATE INDEX. Verify: metrics show p99 → 50ms, logs no more "slow query", traces show Database span → 5ms.

Storage cost tradeoffs:

  • Metrics: cheapest (pre-aggregated). 1 year = $500.
  • Logs: expensive (high volume). 1 month = $500-5000 depending on organization size.
  • Traces: moderate (sampled). Only store 1% of traces = $200-500/month at scale.

Setup strategy: Start with metrics (Prometheus + Grafana). Add logs next (ELK or Loki). Add traces last (Jaeger). Or all-in-one (Datadog) if budget allows.

Correlation via trace_id: When generating a span (trace), extract trace_id. Write trace_id to logs. Now you can jump between systems: find slow trace → get trace_id → search logs for that trace_id.

Critical Production Outage Response (The Discipline)

The mindset: Stabilization first, investigation second. If customer is bleeding money, get them healthy in 3 minutes. Root cause analysis can wait an hour.

Minute 0-1: Communication & Triage

  • Page incident commander (they coordinate comms, you fix)
  • Create incident Slack channel (#incident-2024-08-17)
  • Update status page: "Investigating"
  • Quick check: resources healthy? (CPU, memory, disk). Recent deploy? (git log --oneline).

Minute 1-3: Hypothesis & Stabilization

  • Theory: v2.1.0 deployed 15 minutes ago → likely culprit
  • Action: ROLLBACK (fastest fix when recent deploy exists)
  • kubectl rollout undo deployment/api
  • Result: Error rate 45% → 0.1% in 30 seconds. Incident stabilized.

Minute 3-10: Verify Stability

  • Monitor metrics for 5 minutes (no anomalies)
  • Manual test (curl endpoint, check response)
  • Notify incident commander: "P1 stabilized, rollback deployed"
  • Update status page: "Incident resolved"

After stabilization: Investigation

  • What broke? v2.1.0 had memory leak (goroutines not cleaned up)
  • Why didn't we catch it? No load testing before prod
  • Systemic fix: Add load testing, canary deployment, better code review

Key principle: Recent deploy = suspect #1. Rollback is the right move 80% of the time. If rollback works, incident resolved. Then investigate why it broke. If rollback doesn't work, dig deeper.

Real metric: MTTR (Mean Time To Recovery) before systemic improvements: 47 minutes. After: 18 minutes. The discipline of fast stabilization + systematic prevention is what moved the needle.

Financial Industry Hardening (Defense in Depth)

The regulatory context: Financial firms operate under PCI-DSS, SOX, GLBA, NIST, FedRAMP. Auditors require proof: every action is auditable, every control is logged, every access is authorized.

Identity & Access Layer:

  • Least-privilege IAM: developers get only what they need (not * permissions)
  • Temporary credentials: STS tokens expire automatically (1 hour max)
  • MFA for humans: SSH key alone = 0 access. SSH key + MFA = full access.
  • SSO/federation: Okta/Azure AD + MFA. No local AWS users.
  • Separate prod access: Prod role requires approval gate (humans only, not CI/CD).
  • Audit trail: CloudTrail logs every API call. Who, what, when, where, result.

Network Layer:

  • Private subnets: Databases have NO security group rule allowing 0.0.0.0/0
  • No direct internet access: Database only accepts connections from app tier (10.0.1.0/24)
  • WAF: Blocks SQL injection, XSS, DDoS, geo-blocking
  • VPC Flow Logs: Captures every packet flow. Auditor asks "who accessed database?" → VPC logs prove it.

Data Protection Layer:

  • KMS encryption at rest: S3, RDS, EBS all encrypted with customer-managed key (not AWS-managed)
  • TLS in transit: API ↔ Client (1.2+), API ↔ Database (TLS), API ↔ Cache (TLS)
  • Secrets Manager: Password rotation automated (90-day). Applications read from Secrets Manager, not hardcoded.
  • S3 Block Public Access: No misconfigured bucket is publicly readable

CI/CD Security Layer:

  • Mandatory code review (2 approvals for prod)
  • SAST (Semgrep): Code vulnerabilities
  • Dependency scanning (Snyk): Vulnerable packages
  • Secret scanning (gitleaks): No hardcoded credentials
  • Container image scanning (Trivy): OS vulnerabilities
  • IaC scanning (tfsec): Security groups open to internet? Blocked before deploy.
  • Artifact signing: Every image signed with KMS. Deployment verifies signature.
  • Approval gates: Prod deployments require human approval (MFA)

Runtime Monitoring Layer:

  • CloudTrail: Every API call logged
  • GuardDuty: Detects unusual behavior (1000x failed logins, EC2 to C2 server, etc.)
  • Security Hub: Aggregates findings, shows compliance against PCI-DSS, CIS, SOC 2
  • Config: Continuous compliance monitoring
  • Centralized logs: CloudWatch Logs + ELK for retention and search
  • Alerting: PagerDuty on critical findings
  • Vulnerability management: Automated scanning, patch management, deviation tracking

The integration: These aren't separate concerns. They work together. CloudTrail shows who accessed what. GuardDuty detects if access was unusual. Security Hub flags if the access violates compliance. All three required for audits.

Real cost: $2-5K/month for tooling. One compliance violation = $100K+ fine. ROI is obvious.
