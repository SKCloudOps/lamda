EKS Pod Identity — workload identity flow

1. EKS Pod Identity vs IRSA — Purpose and Difference

Purpose: Both mechanisms allow an EKS pod to access AWS services using temporary AWS credentials without putting long-lived AWS access keys inside the container.

IRSA — IAM Roles for Service Accounts

Pod
 |
 | Kubernetes ServiceAccount
 v
EKS OIDC Provider
 |
 v
IAM Role
 |
 v
S3 / DynamoDB / Secrets Manager / KMS / etc.

With IRSA, you configure:

  • IAM policy
  • IAM role
  • EKS OIDC provider
  • Kubernetes ServiceAccount
  • IAM trust policy restricting which ServiceAccount can assume the role
apiVersion: v1
kind: ServiceAccount
metadata:
  name: report-service
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::123456789012:role/report-role

EKS Pod Identity

Pod
 |
 v
ServiceAccount
 |
 v
EKS Pod Identity Agent
 |
 v
IAM Role
 |
 v
AWS Services

Pod Identity is an AWS-native approach that simplifies workload identity management and avoids configuring the OIDC trust relationship in the same way as IRSA.

Interview answer: “The purpose of both IRSA and EKS Pod Identity is to provide pods with temporary AWS credentials without embedding access keys. IRSA uses the EKS OIDC provider and web identity federation, while EKS Pod Identity uses the EKS Pod Identity Agent. For a new EKS implementation, I would generally prefer Pod Identity unless I have a specific requirement to use IRSA.”

Examples of role-based access:

  • EC2 instance profile → IAM role
  • Lambda execution role → IAM role
  • EKS Pod Identity / IRSA → IAM role
  • GitHub Actions OIDC → IAM role
Best practice: “I avoid long-lived IAM access keys whenever possible. For applications and automation, I prefer IAM roles and temporary credentials.”

main
 |
 +-- hotfix/payment-timeout
          |
          v
     PR + Tests
          |
          v
        main
          |
          v
     Production

A hotfix should not mean bypassing governance. Keep:

  • Mandatory pull request
  • Branch protection
  • Code review
  • Automated tests
  • Security scans
  • Production approval
  • Audit trail
  • Rollback plan
Interview answer: “For urgent production fixes I create a hotfix branch from the production branch or release baseline, apply the smallest possible change, run the required CI/security checks, obtain approval, deploy, validate, and merge the fix back so the change is not lost in future releases.”

Asynchronous invocation

The caller receives a job identifier rather than waiting for the entire workload.

{

Important: Lambda has a 15-minute maximum execution time. Asynchronous invocation does not remove that limit. If the actual processing can exceed 15 minutes, consider Step Functions, ECS/Fargate, AWS Batch, EC2, or EKS depending on the workload.

6. How Does the Caller Know When a Lambda Job Is Completed?

Use a job/status pattern.

POST /reports
      |
      v
Create Job
      |
      +-- jobId = 123
      +-- status = PENDING
      |
      v
SQS
      |
      v
Worker
      |
      v
Generate Report
      |
      +----------> S3
      |
      +----------> DynamoDB
                    status = COMPLETED

The API immediately returns:

{
  "jobId": "123",
  "status": "PENDING"
}

The UI can poll:

GET /jobs/123

Completed response:

{
  "jobId": "123",
  "status": "COMPLETED",
  "downloadUrl": "..."
}

Other notification mechanisms:

  • WebSocket
  • Server-Sent Events
  • SNS
  • Email
  • EventBridge
Interview point: “I decouple job submission from job execution. The caller gets a job ID immediately, and job status is persisted independently of the worker. This makes the design resilient and avoids holding an HTTP connection open for a long-running operation.”

7. DevOps Anti-Patterns

Anti-pattern 1 — Manual deployments

Developer → SSH → Production → Manual Deployment

Problems: human error, poor repeatability, weak auditability.

Better: Git → CI → Tests → Approval → CD → Production.

Anti-pattern 2 — Long-lived branches

Branches remain open for weeks or months, creating merge conflicts, large releases, and difficult integration.

Better: short-lived branches and frequent integration.

Anti-pattern 3 — No automated testing/security

Better:

Other useful examples: manual infrastructure, snowflake servers, no monitoring, shared credentials, “works on my machine,” and no rollback strategy.

8. What Does Shift Left Mean?

Shift left means moving quality, security, testing, compliance, and validation earlier in the software development lifecycle.

9. Blue/Green vs Canary Deployments

Blue/Green

             Load Balancer
                  |
             +----+----+
             |         |
          Blue        Green
           v1           v2

Initially: 100% → Blue
Then:      100% → Green

Advantages: fast rollback, simple traffic switching, predictable deployment.

Disadvantage: can require additional infrastructure because both environments need to exist.

Canary

                 Load Balancer
                      |
              +-------+-------+
              |               |
            v1 95%           v2 5%
                              |
                              v
                            25%
                              |
                              v
                            50%
                              |
                              v
                           100%

Monitor error rate, latency, CPU, logs, and business metrics during each stage.

Heavily stateful environment

“I would not choose solely based on Blue/Green versus Canary. The key issue is state compatibility. I would externalize application state into RDS, DynamoDB, ElastiCache, S3, etc., use backward-compatible database/schema changes, and make sure old and new versions can safely share the state. If that is possible, a controlled canary can reduce deployment risk. If not, I would redesign the state handling before selecting the deployment strategy.”

10. Terraform State Locking and Secrets Management

Collaborative Terraform architecture

Developer A ----Developer B -----+----> Terraform ----> Remote State
Developer C ----/                       |
                                         v
                                  S3 Backend
                                  + Versioning
                                  + Encryption
                                  + State Locking

For multiple engineers:

  • Use centralized remote state.
  • Enable S3 versioning.
  • Encrypt state.
  • Use IAM to restrict state access.
  • Use supported state locking/concurrency protection.
  • Do not use separate local production state.
  • Use CI/CD for controlled production changes.

Secrets

Never hard-code secrets:

password = "MyPassword123"

Instead use:

  • AWS Secrets Manager
  • SSM Parameter Store
  • KMS
  • CI/CD secret stores

Also use least privilege, audit access with CloudTrail, rotate credentials, and mask secrets in CI/CD logs.

11. Kubernetes Diagnostics — Exact Commands and Logs

Start from the symptom, then move from workload → node → AWS infrastructure.

Pod status

kubectl get pods -n <namespace>
kubectl describe pod <pod> -n <namespace>

Look for CrashLoopBackOff, ImagePullBackOff, OOMKilled, FailedMount, FailedScheduling, readiness/liveness failures, and events.

Logs

kubectl logs <pod> -n <namespace>
kubectl logs <pod> -n <namespace> --previous
kubectl logs <pod> -c <container> -n <namespace>

Events

kubectl get events -n <namespace> --sort-by=.lastTimestamp

Deployment

kubectl describe deployment <deployment> -n <namespace>
kubectl rollout status deployment/<deployment>
kubectl rollout history deployment/<deployment>

Resources

kubectl top pod -n <namespace>
kubectl top node

Node

kubectl describe node <node>

Check CPU pressure, memory pressure, disk pressure, allocatable resources, pod capacity, and node events.

AWS/EKS diagnostics

  • CloudWatch Logs
  • CloudWatch metrics
  • Container Insights
  • ALB/NLB metrics
  • Target group health
  • VPC Flow Logs
  • Security Groups
  • EKS control-plane logs
  • Application logs
Diagnostic principle: “I first establish whether the problem is application, pod, node, Kubernetes control plane, network/load balancer, database, or AWS infrastructure. I use events and metrics to narrow the scope before changing anything.”

Example

    cpu: "250m"
    memory: "512Mi"

    cpu: "1"
    memory: "1Gi"

Requests

Requests tell the scheduler how much resource the workload needs for placement.

Limits

Limits define the maximum resource the container can consume.

How to determine the values

Useful tools:

  • CloudWatch
  • Prometheus
  • Grafana
  • Kubernetes Metrics Server

If memory consumption reaches the configured limit, the container can be terminated with OOMKilled.

Use HPA for pod scaling and Karpenter/Cluster Autoscaler for node capacity. Avoid setting memory limits too low.

Interview answer: “I don't choose requests and limits randomly. I establish a baseline from historical metrics, validate it with load testing, account for peak usage and a safety margin, then continuously tune based on production observations.”

18. Financial Industry Hardening Guidelines

For a financial environment, hardening should be treated as defense in depth, least privilege, strong auditability, and controlled change management.

Identity and access

  • Least-privilege IAM policies
  • IAM roles instead of long-lived credentials
  • MFA for human access
  • SSO/federation where possible
  • Separate production access from development access
  • Short-lived credentials
  • Regular access reviews

Network

  • Private subnets for application/database tiers
  • No direct internet access to databases
  • Security Groups with minimum required ports
  • WAF for internet-facing APIs
  • Network segmentation
  • VPC Flow Logs

Data protection

  • KMS encryption at rest
  • TLS encryption in transit
  • Secrets Manager/Parameter Store
  • Secret rotation
  • S3 Block Public Access
  • Backup and recovery testing

CI/CD security

  • Branch protection
  • Mandatory code review
  • SAST
  • Dependency scanning
  • Secret scanning
  • Container image scanning
  • IaC scanning
  • Signed/approved artifacts where required
  • Production approval gates

Runtime and monitoring

  • CloudWatch
  • CloudTrail
  • GuardDuty
  • Security Hub
  • Config
  • Centralized logs
  • Alerting
  • Vulnerability management
Interview answer: “In a financial environment, I focus on least privilege, encryption, network segmentation, strong identity controls, immutable audit trails, vulnerability management, controlled deployments, continuous monitoring, backup/recovery, and evidence that controls are actually enforced.”

19. General DevOps Interview Answer Pattern

For architecture and troubleshooting questions, use this structure:

1. Define the concept
        ↓
2. Explain why it is needed
        ↓
3. Give an AWS/Kubernetes example
        ↓
4. Explain security and reliability
        ↓
5. Explain monitoring
        ↓
6. Connect it to real-world experience

Example: “How do you secure an EKS application?”

“I use IAM roles through EKS Pod Identity, Kubernetes RBAC for cluster permissions, private worker nodes, security groups for network controls, Secrets Manager for secrets, KMS for encryption, image scanning in CI, security policies at runtime, and CloudWatch/Prometheus for monitoring. I also apply least privilege and shift-left security checks in the CI/CD pipeline.”

Senior-level mindset

  • Don't only name tools; explain why you selected them.
  • Always mention security and least privilege.
  • Always mention observability for production systems.
  • Explain failure handling and rollback.
  • Discuss HA and multi-AZ where relevant.
  • For stateful systems, discuss state consistency and backward compatibility.
  • For long-running work, discuss asynchronous architecture and job status.
  • For incidents, explain mitigation first and root cause second.
