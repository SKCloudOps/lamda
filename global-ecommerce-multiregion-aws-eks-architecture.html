Architecture reference

How this system is put together

The diagram above is a warm-standby, two-region deployment: the edge is active/active in both regions, while the data plane has a single writer in us-east-1 and a promotable reader in eu-west-1. Everything below explains what each box does, how state is kept in sync between the regions, which guardrails stop a bad change from reaching production, and what actually happens when something fails. Figures quoted here are design targets to validate in game days, not vendor SLAs.

1Request path, end to end

This is the path the animated comets trace. Static assets stop at step 3; a checkout write travels the whole way.

  1. Client resolves the hostnameRoute 53 answers with latency-based routing, so a shopper in Frankfurt gets the eu-west-1 record and a shopper in Ohio gets us-east-1. Health checks attached to each record remove a region that stops answering.
  2. Anycast entry and DDoS absorptionTraffic lands on CloudFront (HTTP/S) or Global Accelerator (raw TCP/UDP for the mobile socket layer). Shield Advanced absorbs L3/L4 volumetric attacks before anything reaches an origin.
  3. Edge cache and edge computeCloudFront serves cached product images and catalogue responses from the nearest PoP. Global WAF rules run here — SQLi/XSS signatures, bot control, per-IP rate limits. Lambda@Edge / CloudFront Functions handle A/B bucketing, geo personalisation and header rewrites without a round trip to origin.
  4. Regional ingressA cache miss goes to the regional ALB, fronted by its own regional WAF web ACL. The ALB terminates TLS with an ACM certificate and routes by host/path across three AZs. Partner and mobile BFF traffic enters through API Gateway instead.
  5. Into the clusterThe AWS Load Balancer Controller has registered pod IPs directly as ALB target group targets. The request hits an Envoy sidecar, which applies mTLS, retries, timeouts and circuit breaking before handing off to the service container.
  6. Service-to-service workCheckout calls Payment, which invokes the fraud-detection Lambda synchronously for a risk score. Reads hit ElastiCache first; a miss falls through to Aurora via RDS Proxy or to DynamoDB for cart and session state.
  7. Commit and fan outThe order row is written to Aurora, then an OrderPlaced event goes to EventBridge. SQS buffers fulfilment work, SNS fans out customer notifications, and Step Functions drives the multi-step fulfilment saga with compensating actions if a step fails.
  8. Asynchronously, everywhereClickstream and inventory deltas stream through MSK. Uploaded images trigger the resize Lambda from an S3 event. Every hop emits metrics, logs and an X-Ray trace segment.

Each store replicates differently, and the differences are what make or break a failover. The table below is the single most important thing to internalise about this architecture.

The effective RPO is set by the slowest store in the path

An order is not one write. It is an Aurora row, a DynamoDB cart update, an S3 receipt and an EventBridge event. Quoting "RPO ≈ 1 second" because that is Aurora's number is wrong: if the receipt PDF lands in S3 and the region fails 30 seconds later, that object may not have replicated. Per business transaction, the RPO is the worst case across every store it touched.

This is why the design leans on the SQS and EventBridge buffer. Work that has been accepted but not yet completed survives in a queue rather than in the memory of a pod that no longer exists.

Rules the application has to honour

  • Writes are pinned to the writer region. The secondary is a reader. Either route write paths back to us-east-1, or enable Aurora write forwarding and accept the added cross-Atlantic latency on every write.
  • No read-your-writes across regions. A write committed in us-east-1 and read from the eu-west-1 reader a few hundred milliseconds later may not be there. Read back from the writer within a session, or from DynamoDB, which is multi-active.
  • Every mutating endpoint takes an idempotency key. A retry after a failover must not create a second order or capture a second payment. This is the single most common source of data damage during DR.
  • Cache invalidation crosses regions. ElastiCache Global Datastore replicates the primary's writes, but an invalidation issued against the wrong endpoint silently does nothing.
  • KMS keys must exist in both regions. S3 CRR of SSE-KMS objects fails unless the destination has a usable key — use multi-Region keys or an explicit destination key in the replication rule.

4Security guardrails

Guardrails are graded by what happens when someone tries to cross them. A preventative guardrail makes the action fail. A detective control tells you it happened. The goal is that the expensive mistakes are all in the first category.

Why GitOps is itself a security control

Because ArgoCD reconciles continuously, an operator who edits the cluster by hand is reverted within minutes. That removes standing human write access to production as a requirement: the pipeline identity is the only thing that needs it, and every change carries a commit, a reviewer and a diff.

Regional failover runbook

  1. Confirm, do not reactA composite alarm across several independent signals must fire — a single failing health check is not a region outage. Failing over on a false positive costs an Aurora promotion and a cold cache for nothing.
  2. Stop the bleeding at DNSRoute 53 health checks pull the failed region automatically. Client-observed recovery is bounded by record TTL, which is why TTL is kept at 60 seconds. Global Accelerator traffic moves in seconds because anycast does not wait for DNS.
  3. Promote the data tierPromote the Aurora global secondary — typically under a minute — then ElastiCache. Until Aurora promotion completes the surviving region serves reads but rejects writes, so this step is the critical path.
  4. Scale into the loadeu-west-1 was carrying its own share, not all of it. Karpenter and HPA scale out, but a cold ElastiCache means Aurora briefly absorbs the full read volume — pre-warm the cache or plan for the spike.
  5. Drain the buffersWork accepted before the failure sits in SQS and MSK. Consumers restart from translated offsets, so duplicate delivery is expected — this is what the idempotency keys are for.
  6. Validate before declaring recoveryRun synthetic checkouts end to end. Traffic arriving is not the same as orders completing.
  7. Fail back deliberatelyFailback is a planned change, not an emergency. Rebuild us-east-1 as the new secondary, let replication catch up fully, then reverse roles during a low-traffic window.

A recovery plan that has not been rehearsed is a hypothesis

Regional failover should be exercised on a schedule, not discovered during an incident. The drills worth running: a real Aurora global failover in a pre-production copy; restoring a backup and verifying the restored data rather than just the job status; killing an AZ's worth of nodes to confirm PDBs and Karpenter behave; and forcing Spot reclamation under load. Each one turns an assumption in this document into a measurement.

6Trade-offs this design accepts

  • Warm standby, not active/active for writes. A single Aurora writer keeps the data model simple and removes conflict resolution entirely, at the cost of a promotion step in the failover path. True active/active writes would mean either sharding by geography or accepting conflict resolution across the whole order model.
  • The secondary region is largely idle capacity. It serves its own read traffic but is provisioned to absorb both regions. That is the premium being paid for a single-digit-minute RTO.
  • Mixed consistency models. Aurora is strongly consistent, DynamoDB is multi-active with last-writer-wins, and S3 is eventually consistent across regions. Developers have to know which store they are touching — this is a real, permanent cognitive cost.
  • Spot capacity trades cost for churn. Roughly a 70% saving on stateless tiers, paid for with interruption handling, diversified pools and graceful shutdown that has to actually work.
  • The mesh adds a hop. Envoy sidecars bring uniform mTLS, retries and telemetry, and they add latency and per-pod memory. Worth it at nine services; questionable at three.
  • DNS TTL is a floor on failover. Nothing in the HTTP path recovers faster than the TTL clients have cached, which is exactly why Global Accelerator carries the traffic that cannot tolerate it.
