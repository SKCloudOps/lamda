1. Architecture Overview

This is a production-grade Amazon EKS platform designed for highly available enterprise workloads.

2. End-to-End Request Flow

User | v Route 53 | v CloudFront | v AWS WAF / Shield | v Application Load Balancer | v Ingress | v Kubernetes Service | v Ready Pod | v Application | +------> ElastiCache +------> RDS / Aurora +------> SQS / SNS / MSK +------> Other Internal APIs
  • Route 53 provides DNS.
  • CloudFront provides edge delivery and optional caching.
  • WAF filters malicious HTTP traffic.
  • Shield provides DDoS protection.
  • ALB provides Layer-7 load balancing.
  • Ingress defines Kubernetes HTTP routing.
  • Service provides stable access to Pods.
  • Pods run the application.

3. AWS VPC and Multi-AZ Network

VPC 10.0.0.0/16 +-------------------+-------------------+-------------------+ | Availability Zone A| Availability Zone B| Availability Zone C| | Public Subnet A | Public Subnet B | Public Subnet C | | NAT Gateway | NAT Gateway | NAT Gateway | | | | | | Private Subnet A | Private Subnet B | Private Subnet C | | EKS Nodes / Pods | EKS Nodes / Pods | EKS Nodes / Pods | +-------------------+-------------------+-------------------+

Worker nodes and application Pods should normally run in private subnets. Public load balancers and NAT gateways can reside in public subnets.

Architectural principle: The load balancer can be public while the application compute layer remains private.

6. Worker Nodes and Node Groups

  • kubelet manages Pods.

  • VPC CNI provides Pod networking.

Production node groups should span multiple AZs and use labels, taints/tolerations, affinity rules and autoscaling where appropriate.

7. Pods and Pod Networking

Worker Node | +-- Pod: web-1 | +-- Application Container | +-- Sidecar Container (optional) | +-- Pod: api-1 | +-- Pod: api-2

With AWS VPC CNI, Pods receive VPC networking addresses according to the cluster configuration.

Key interview point: A Pod being Running does not necessarily mean it is ready to receive traffic. Readiness determines whether it should be included behind a Service.

10. Ingress → Service → Replica → Pod Routing

Client | v ALB | v Ingress Rule | v svc-api | v EndpointSlice | +----------------+----------------+ | | | Pod api-1 Pod api-2 Pod api-3 Ready Ready Ready | | | +----------------+----------------+ Application
Pod process healthy ↓ Readiness probe passes ↓ Pod becomes Ready ↓ EndpointSlice includes Pod ↓ Service can send traffic ↓ Ingress / ALB can reach application
Common 503 root cause: Pods may be Running but not Ready. If there are no healthy endpoints, the load balancer can return 503.

HPA scales Pods. Cluster Autoscaler adjusts node groups. Karpenter can dynamically provision suitable compute based on pending workload requirements.

15. IAM and Workload Identity

Kubernetes ServiceAccount | v EKS Pod Identity / IRSA | v IAM Role | v AWS APIs | +-- S3 +-- SQS +-- Secrets Manager +-- Other AWS Services
Least privilege: Give each workload only the AWS permissions it actually needs. Never put long-lived AWS access keys into application containers.

21. Production Failure Scenarios

ALB returns 503

ALB | v Ingress | v Service | v EndpointSlice | +-- No Ready Pods | v 503
kubectl get ingress
kubectl describe ingress <ingress>
kubectl get svc
kubectl get endpoints
kubectl get endpointslice
kubectl get pods
kubectl describe pod <pod>

Pods are Running but not Ready

Investigate readiness probes, health endpoints, ports, application startup and dependencies.

Pods are Pending

Investigate CPU/memory requests, node capacity, taints/tolerations, affinity, topology rules and PVCs.

Node is NotReady

Check node conditions, kubelet, container runtime, CNI, EC2 health, disk pressure, memory pressure and networking.

Application is slow

Client → CloudFront → WAF → ALB → Ingress → Service → Pod → Cache / DB / External API

Correlate ALB latency, Pod metrics, application logs, traces and database metrics.

22. Architect-Level Interview Explanation

Recommended answer:

"For a production EKS platform, I would design the cluster across multiple Availability Zones with worker nodes in private subnets. Internet traffic would enter through Route 53 and, where appropriate, CloudFront and WAF before reaching a multi-AZ Application Load Balancer. The AWS Load Balancer Controller would integrate the ALB with Kubernetes Ingress resources.

The Ingress would route requests to Kubernetes Services, and Services would distribute traffic across Ready Pods managed by Deployments. I would use readiness, liveness and startup probes to protect application availability during deployments and failures.

For scalability, HPA would scale Pods based on application metrics, while Karpenter or Cluster Autoscaler would provide additional compute capacity when Pods cannot be scheduled.

The workloads would use IAM-based workload identity instead of static AWS credentials. Secrets would be managed through AWS Secrets Manager, data would be stored in RDS or Aurora, caching would use ElastiCache, and asynchronous workloads could use SQS or MSK.

For delivery, GitHub Actions would build, test and scan container images before publishing them to ECR. Argo CD would reconcile the desired Kubernetes state from Git into EKS.

For observability, I would collect logs, metrics and traces using CloudWatch, Prometheus/AMP, Grafana and OpenTelemetry/X-Ray. Security would use WAF, IAM, RBAC, NetworkPolicy, KMS, Secrets Manager, image scanning, GuardDuty and centralized audit logging.

Finally, I would design multi-AZ resilience, PodDisruptionBudgets, backups, disaster recovery and clear RTO/RPO targets so the platform is not only scalable but also operationally resilient."

What makes this architect-level?

  • Complete request-path understanding.
  • Separation of edge, network, compute, application and data layers.
  • Kubernetes internals plus AWS integration.
  • Security and workload identity.
  • CI/CD and GitOps.
  • Observability and autoscaling.
  • Failure recovery and disaster recovery.
  • Understanding of trade-offs, not just service names.
