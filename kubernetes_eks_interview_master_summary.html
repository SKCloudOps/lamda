1. Kubernetes Networking

Every Pod normally receives its own IP address. Pods can communicate with Pods on the same node, different nodes, and different namespaces. The implementation depends on the CNI.

Pod A ───────────────► Pod B
       Pod IP

EKS commonly:
AWS VPC CNI → integrates Pod networking with the AWS VPC.
Interview: Kubernetes follows a flat Pod networking model where Pods can communicate directly without NAT in the normal Pod-to-Pod model. The CNI implements the networking.

Cross-namespace communication

http://user-service.backend.svc.cluster.local:8080

Format: <service>.<namespace>.svc.cluster.local

3. Startup vs Readiness vs Liveness

ProbeQuestionFailure behavior
StartupHas the application finished starting?Protects slow startup
ReadinessCan this Pod receive traffic?Removes Pod from Service endpoints
LivenessIs the application still alive?Container can be restarted
Startup   → Can you start?
Readiness → Can you receive traffic?
Liveness  → Are you still alive?

4. CrashLoopBackOff

CrashLoopBackOff is a symptom: the container starts, crashes, Kubernetes restarts it, and Kubernetes increases the restart backoff.

Common causes

  • Application startup error
  • Bad command or arguments
  • Missing ConfigMap/Secret
  • Bad image
  • OOMKilled
  • Liveness probe failure
  • Database/dependency unavailable
  • Permission problems

Commands

kubectl get pods -n <namespace>
kubectl describe pod <pod> -n <namespace>
kubectl logs <pod> -n <namespace>
kubectl logs <pod> -n <namespace> --previous
kubectl logs -f <pod> -n <namespace>
kubectl get events -n <namespace> --sort-by='.lastTimestamp'
kubectl top pod <pod> -n <namespace>
Most important: kubectl logs <pod> --previous when a container is repeatedly crashing.

6. Taints, Tolerations, Node Affinity & Pod Anti-Affinity

Taint = Node

kubectl taint nodes <node> workload=gpu:NoSchedule
kubectl describe node <node>
kubectl taint nodes <node> workload=gpu:NoSchedule-

Toleration = Pod

tolerations:
  - key: workload
    operator: Equal
    value: gpu
    effect: NoSchedule

Toleration allows a Pod to run on a tainted node; it does not force the Pod onto that node.

Node Affinity

Question: Which nodes should my Pod run on?

affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
        - matchExpressions:
            - key: workload
              operator: In
              values:
                - gpu

Pod Anti-Affinity

Question: Which other Pods should my Pod avoid?

affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app: user-service
        topologyKey: kubernetes.io/hostname

Topology Spread Constraints

topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        app: user-service

Scheduling troubleshooting

kubectl get pods
kubectl describe pod <pod>
kubectl get nodes --show-labels
kubectl describe node <node>
kubectl top nodes

7. NetworkPolicy

NetworkPolicy controls which network traffic is allowed to/from Pods. Think of it as a firewall for Pod communication.

WebApp
  ├──► User Service      ✅
  ├──► Order Service     ✅
  └──► Database          ❌

Example

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: user-service-policy
  namespace: backend
spec:
  podSelector:
    matchLabels:
      app: user-service
  policyTypes:
    - Ingress
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              name: frontend
      ports:
        - protocol: TCP
          port: 8080
kubectl get networkpolicy -A
kubectl get networkpolicy -n <namespace>
kubectl describe networkpolicy <policy> -n <namespace>
Important: NetworkPolicy enforcement depends on the CNI/networking implementation.

8. Multi-AZ EKS

                    AWS Region
          ┌────────────┼────────────┐
          ▼            ▼            ▼
        AZ-1         AZ-2         AZ-3
          │            │            │
       Node-1       Node-2       Node-3
          │            │            │
       Pods          Pods          Pods

Multi-AZ protects against Availability Zone failure. It does not mean traffic is guaranteed to be exactly 33/33/33 across three AZs.

With an AWS ALB, traffic is distributed among healthy registered targets according to the load-balancing behavior. Cross-zone load balancing affects whether traffic can be distributed across AZ boundaries.

Key distinction

Multi-AZ
→ Where are my Pods?
→ Infrastructure availability

Canary
→ Which application version gets traffic?
→ Deployment risk reduction

9. Blue-Green vs Canary

Blue-Green

Blue  = v1 → 100%
Green = v2 → 0%

After validation:

Blue  = v1 → 0%
Green = v2 → 100%

Memory: Blue-Green = switch.

  • Very fast rollback
  • Easy to understand
  • Requires additional capacity

Canary

v1 = 95%, v2 = 5%
      ↓
v1 = 75%, v2 = 25%
      ↓
v1 = 50%, v2 = 50%
      ↓
v1 = 0%,  v2 = 100%

Memory: Canary = gradual shift.

Monitor error rate, latency, CPU, memory, logs, and business metrics. Strong observability is required.

13. Securing an EKS Cluster

  1. IAM / EKS Access: least privilege and controlled cluster access.
  2. Kubernetes RBAC: restrict Kubernetes operations.
  3. Network: private subnets, Security Groups, NetworkPolicy, VPC endpoints where appropriate.
  4. Pod Security: non-root, no unnecessary privileges, restricted capabilities.
  5. Secrets: Secrets Manager + KMS instead of Git/static credentials.
  6. Image Security: scan images and use trusted/minimal images.
  7. Encryption: encryption at rest and TLS in transit.
  8. CI/CD: SAST, dependency scan, secret scan, IaC scan, image scan, OIDC.
  9. Monitoring: CloudTrail, EKS audit/control-plane logs, GuardDuty, Security Hub, CloudWatch/Prometheus/Grafana as appropriate.
GitHub Actions
     ↓
OIDC
     ↓
AWS IAM Role
     ↓
EKS

Pod security context

securityContext:
  runAsNonRoot: true
  allowPrivilegeEscalation: false
  readOnlyRootFilesystem: true
