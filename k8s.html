1. Explain Kubernetes architecture

Kubernetes has two major parts: the Control Plane and Worker Nodes.

Control Plane

  • API Server — entry point for Kubernetes operations.
  • etcd — stores Kubernetes cluster state.
  • Scheduler — decides which node should run a Pod.
  • Controller Manager — continuously makes actual state match desired state.
  • Cloud Controller Manager — integrates Kubernetes with cloud providers such as AWS.

Worker Nodes

  • kubelet — manages Pods on the node.
  • Container Runtime — runs containers, typically containerd.
  • kube-proxy — supports Kubernetes Service networking.
  • Pods — run application containers.
Interview statement: Kubernetes follows a desired-state model. I declare desired state through the API server, store the state in etcd, and controllers continuously work to make the actual cluster state match that desired state.

2. What happens when you create a Deployment?

kubectl apply -f deployment.yaml
kubectl | v API Server | v etcd | v Deployment Controller | v ReplicaSet | v Scheduler | v Worker Node | v kubelet | v Container Runtime | v Pod

The API server receives the desired state. The Deployment Controller creates or updates a ReplicaSet. The ReplicaSet ensures the required number of Pods exist. The Scheduler assigns unscheduled Pods to nodes. kubelet asks the container runtime to create the containers.

3. Deployment vs ReplicaSet

A ReplicaSet ensures a specific number of Pods are running.

A Deployment manages ReplicaSets and provides:

  • Rolling updates
  • Rollbacks
  • Version management
  • Replica management
Deployment | +---- ReplicaSet v1 | | | +-- Pod | +-- Pod | +---- ReplicaSet v2 | +-- Pod +-- Pod

For stateless applications, normally use a Deployment rather than managing ReplicaSets directly.

4. How does Kubernetes perform a rolling deployment?

Suppose there are 4 replicas and version v2 is being deployed.

v1 Pods: 4 v2 Pods: 0 ↓ v1 Pods: 3 v2 Pods: 1 ↓ v1 Pods: 2 v2 Pods: 2 ↓ v1 Pods: 1 v2 Pods: 3 ↓ v1 Pods: 0 v2 Pods: 4
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 1
    maxSurge: 1

5. What are maxSurge and maxUnavailable?

Suppose:

replicas: 10
maxSurge: 2
maxUnavailable: 1

maxSurge is the maximum number of Pods that can temporarily exist above the desired replica count. Here Kubernetes can have up to 12 Pods.

maxUnavailable is the maximum number of Pods that can be unavailable during deployment. With 10 replicas and maxUnavailable 1, Kubernetes aims to keep at least 9 available.

6. What happens if a Pod crashes?

Desired replicas = 3 Pod 1 → Running Pod 2 → Running Pod 3 → Crash ReplicaSet sees only 2 healthy replicas ↓ Creates/replaces Pod ↓ Eventually 3 replicas again

Kubernetes controllers maintain the desired state. This is the basis of Kubernetes self-healing for workloads managed by controllers.

7. Pod vs Container

A Pod is the smallest deployable unit in Kubernetes. A Pod can contain one or multiple containers.

Pod | +-- Application Container

Containers in the same Pod share the network namespace, IP address, localhost, and can share volumes.

8. Why not normally put multiple application containers in one Pod?

Containers in the same Pod share a lifecycle and scale together. If App A needs 10 replicas but App B needs 2, putting them in one Pod forces them to scale together.

Deployment A → 10 Pods Deployment B → 2 Pods

Multiple containers in one Pod are most useful for tightly coupled sidecars such as logging agents, service mesh proxies, security agents, proxies, or configuration helpers.

9. What is a Kubernetes Service?

Pods are ephemeral and their IP addresses can change. A Service provides a stable networking abstraction and selects Pods using labels.

Service | +--------+--------+ | | | Pod Pod Pod

10. ClusterIP vs NodePort vs LoadBalancer

ClusterIP

Internal access. It is the default Service type.

NodePort

Exposes a Service through a port on every node.

Client → NodeIP:30080 → Service → Pods

LoadBalancer

Integrates with a cloud provider to expose a load balancer. In AWS this can integrate with AWS load-balancing services depending on the Service and controller configuration.

11. In AWS EKS, how would you expose an application?

Internet | Route 53 | CloudFront | WAF | ALB | Ingress | Kubernetes Service | Pods

For EKS, a common approach is the AWS Load Balancer Controller, which creates and manages AWS load balancers from Kubernetes resources.

12. Ingress vs Service

A Service provides connectivity to a group of Pods. Ingress provides HTTP/HTTPS routing rules.

api.company.com | Ingress / \ /users /orders | | User Order Service Service

13. What is a readiness probe?

A readiness probe answers: Is this Pod ready to receive traffic?

readinessProbe:
  httpGet:
    path: /health
    port: 8080

If readiness fails, the Pod can remain Running but should not receive traffic through the Service.

14. Liveness vs Readiness vs Startup

  • Readiness — determines whether the Pod should receive traffic.
  • Liveness — determines whether the application is still healthy; repeated failure can cause a container restart.
  • Startup — protects slow-starting applications before liveness/readiness checks become active.
Application starts | | slow initialization v Startup probe succeeds | v Liveness / Readiness become active

15. Why can a Pod be Running but not Ready?

Possible reasons include:

  • Readiness probe failure
  • Application still initializing
  • Wrong health-check endpoint
  • Wrong port
  • Dependency unavailable
  • Database connection failure
  • Configuration issue
  • Secret missing
  • Network connectivity issue
kubectl get pods
kubectl describe pod <pod>
kubectl logs <pod>
kubectl get events

16. How do you troubleshoot CrashLoopBackOff?

kubectl get pods
kubectl describe pod <pod>
kubectl logs <pod>
kubectl logs <pod> --previous
kubectl get events

Investigate application errors, bad environment variables, missing Secrets/ConfigMaps, database connectivity, permission issues, OOMKilled, incorrect entrypoint, and liveness probe failures.

Senior-level approach: Don't immediately restart the Pod. First determine why Kubernetes is restarting it.

17. What is OOMKilled?

OOM means Out Of Memory. If a container exceeds its memory limit, it can be terminated with an OOMKilled reason.

resources:
  requests:
    memory: "512Mi"
  limits:
    memory: "1Gi"

Check with:

kubectl describe pod <pod>

Then investigate application memory behavior, leaks, workload characteristics, and resource sizing.

18. Requests vs Limits

Request: resource amount Kubernetes uses when scheduling a Pod.

requests:
  cpu: 500m
  memory: 512Mi

Limit: maximum resource the container can consume.

limits:
  cpu: "1"
  memory: "1Gi"
Remember: Requests influence scheduling; limits constrain runtime usage.

19. What happens if CPU limit is exceeded?

CPU is generally throttled. Memory behaves differently: exceeding the memory limit can result in the container being killed with an OOMKilled condition.

20. How does Kubernetes decide which node gets a Pod?

The Scheduler considers CPU/memory requests, node selectors, affinity, anti-affinity, taints, tolerations, topology constraints, and scheduling policies.

Pod | Scheduler | +-- Node A ❌ insufficient CPU +-- Node B ❌ taint +-- Node C ✅

21. Taints and Tolerations

A taint says: don't schedule Pods here unless they tolerate this.

Node:
taint: workload=database:NoSchedule
tolerations:
- key: workload
  operator: Equal
  value: database
  effect: NoSchedule

Useful for dedicated GPU, database, system, or high-memory nodes.

22. Node Affinity vs Pod Anti-Affinity

Node Affinity controls which nodes a Pod should run on.

Pod Anti-Affinity controls which Pods should not be placed together.

High availability example: Node A → payment Pod Node B → payment Pod Node C → payment Pod rather than: Node A → payment Pod Node A → payment Pod Node A → payment Pod

23. ConfigMap vs Secret

ConfigMap is for non-sensitive configuration such as database host, log level, and environment name.

Secret is intended for sensitive values such as passwords, API keys, and tokens.

Senior-level point: Kubernetes Secrets are not automatically a complete enterprise secrets-management solution. In AWS, consider integrating with AWS Secrets Manager or Parameter Store and mechanisms such as the Secrets Store CSI Driver where appropriate.

24. How does Kubernetes networking work?

Pods normally receive their own IP addresses and can communicate with other Pods without requiring NAT in the normal Kubernetes networking model. The implementation depends on the CNI.

Pod A: 10.0.1.10 | | network v Pod B: 10.0.2.20

In EKS, AWS VPC CNI is commonly used.

25. What is the AWS VPC CNI?

AWS VPC CNI allows Kubernetes Pods to participate directly in AWS VPC networking using AWS networking resources/IP addresses.

VPC | +-- EC2 Node | | | +-- Pod IP | +-- Pod IP | +-- EC2 Node | +-- Pod IP

This supports connectivity to VPC resources such as RDS, ElastiCache, and internal load balancers.

26. How do you troubleshoot a Pod that cannot connect to RDS?

Pod ↓ Pod IP ↓ Node / VPC networking ↓ Security Group ↓ Network ACL ↓ Route Table ↓ RDS
kubectl exec -it <pod> -- nslookup <rds-host>
kubectl exec -it <pod> -- nc -vz <rds-host> 3306

Check DNS, security groups, network ACLs, routes, RDS security group, listener/port, credentials, and NetworkPolicy where applicable.

27. What is NetworkPolicy?

NetworkPolicy controls which Pods can communicate with other Pods or networks.

Frontend | v Backend ✅ | v Database ❌ direct access

Policies can use namespaces, Pod labels, IP blocks, and ports.

NetworkPolicy enforcement depends on the networking implementation/configuration. Defining a policy does not by itself guarantee enforcement in every cluster.

28. How does Kubernetes provide high availability?

Load Balancer | +---------+---------+ | | | Node A Node B Node C | | | Pod A Pod B Pod C

Use multiple worker nodes, multiple Availability Zones, multiple Pod replicas, topology spread/anti-affinity, PodDisruptionBudget, and appropriate autoscaling. In EKS, spread workloads across multiple AZs.

29. What is PodDisruptionBudget?

minAvailable: 2

A PDB protects availability during voluntary disruptions such as node maintenance, cluster upgrades, and node draining.

A PDB does not protect against every type of failure, such as an unexpected node crash.

30. HPA vs Cluster Autoscaler vs Karpenter

Traffic | HPA | More Pods | Pods Pending | Karpenter / Node Scaling | New EC2 capacity | Pods Scheduled
  • HPA scales Pods.
  • Cluster Autoscaler scales nodes based on unschedulable Pods and node group configuration.
  • Karpenter dynamically provisions suitable compute capacity based on pending workload requirements.

31. Does HPA scale only on CPU?

No. HPA can use CPU, memory, custom metrics, and external metrics.

For production workloads, application/business metrics can sometimes be better than CPU, such as queue depth, requests per second, Kafka lag, or active requests.

32. How would you deploy a zero-downtime application?

Deployment + Readiness Probe + RollingUpdate + Multiple Replicas + PodDisruptionBudget + Topology Spread + Load Balancer

Only ready Pods receive traffic, while multiple replicas and appropriate rollout settings maintain availability during deployment.

33. Blue-Green vs Canary deployment

Blue-Green

Blue → v1 Green → v2 Traffic switches from Blue to Green.

Rollback can be fast because the old environment remains available.

Canary

v1 → 90% v2 → 10% then v1 → 50% v2 → 50% then v2 → 100%

Canary reduces deployment risk by gradually increasing exposure.

34. How would you troubleshoot high latency in an EKS application?

Client ↓ CloudFront ↓ WAF ↓ ALB ↓ Ingress ↓ Service ↓ Pod ↓ Database / Cache / External API

Kubernetes

  • Pod CPU and memory
  • CPU throttling
  • Restarts
  • HPA behavior
  • Scheduling
  • Network latency

Application

  • Application logs
  • Thread pool
  • Connection pool
  • Garbage collection
  • Dependency latency

AWS

  • ALB latency
  • Target response time
  • RDS performance
  • ElastiCache
  • Network metrics

Useful observability tools include CloudWatch, Prometheus, Grafana, OpenTelemetry/ADOT, and distributed tracing where implemented.

35. How do you debug Pending Pods?

kubectl get pods
kubectl describe pod <pod>

Look at Events. Common causes:

  • Insufficient CPU
  • Insufficient memory
  • No matching node selector
  • Taint without toleration
  • PVC unavailable
  • Impossible affinity rules
  • Node capacity exhausted
0/10 nodes are available:
5 insufficient memory
3 didn't match node selector
2 had taint

36. What happens when you run kubectl drain?

kubectl drain prepares a node for maintenance. Workloads are evicted when eligible and controllers recreate them on other nodes.

kubectl drain node-1 --ignore-daemonsets
kubectl uncordon node-1

37. Cordon vs Drain

Cordon prevents new Pods from being scheduled but leaves existing Pods running.

kubectl cordon node-1

Drain cordons the node and evicts eligible workloads.

kubectl drain node-1

38. How do you secure an EKS cluster?

Identity ↓ IAM ↓ EKS Authentication ↓ RBAC ↓ NetworkPolicy ↓ Security Groups ↓ Secrets Management ↓ Image Security ↓ Runtime Security ↓ Audit / Monitoring
  • Least-privilege IAM
  • EKS Pod Identity / IRSA where appropriate
  • Kubernetes RBAC
  • Private API endpoint where appropriate
  • KMS encryption
  • Secrets Manager
  • Image scanning
  • Network policies
  • Security groups
  • CloudTrail
  • GuardDuty
  • Audit logging

39. Pod Identity vs IRSA

Both solve the workload identity problem without putting static AWS credentials inside Pods.

IRSA

ServiceAccount | OIDC | IAM Role | AWS Permissions

EKS Pod Identity

AWS provides a newer mechanism that simplifies associating IAM roles with Kubernetes workloads.

Interview answer: Both solve workload identity. For new EKS implementations, I would evaluate EKS Pod Identity first, while IRSA remains important for existing clusters and compatibility.

40. What is RBAC?

RBAC means Role-Based Access Control. It controls who can perform which actions on which Kubernetes resources.

Who | Role | Actions | Resources

Resources can include Pods, Deployments, Services, Secrets, and ConfigMaps.

41. Role vs ClusterRole

Role is namespace-scoped.

ClusterRole is cluster-scoped or can be bound into namespaces depending on how it is used.

42. How would you implement GitOps for Kubernetes?

Developer | Git | CI Pipeline | Build / Test / Scan | Container Registry | GitOps Repository | Argo CD / Flux | Kubernetes

The key principle is that Git becomes the source of truth for desired Kubernetes state. CI builds and publishes artifacts; GitOps CD reconciles the cluster to the desired state.

43. Why shouldn't CI directly run kubectl apply in a mature GitOps architecture?

CI | Build / Test / Scan | Push Image | Update Git Desired State | Argo CD | Kubernetes

Advantages include auditability, Git history, easy rollback, drift detection, separation of CI and CD, and reconciliation.

44. How do you handle secrets in GitOps?

Do not commit plain-text secrets into Git.

Possible approaches include AWS Secrets Manager, Parameter Store, Secrets Store CSI Driver, SOPS, or Sealed Secrets, depending on the security model.

AWS Secrets Manager | Secrets Store CSI Driver | Kubernetes Pod

45. What is etcd and why is it critical?

etcd is the Kubernetes distributed key-value store. It contains cluster state such as Deployments, Pods, Services, ConfigMaps, Secrets, RBAC, and cluster configuration.

Therefore backups, encryption at rest, high availability, and tightly controlled access are important.

In EKS, AWS manages the Kubernetes control plane and its underlying control-plane infrastructure.

46. What happens if etcd goes down?

Existing workloads may continue running for some time because kubelets and containers are already operating. However, the control plane cannot reliably persist or retrieve cluster state.

Problems can occur with new deployments, scheduling, scaling, controllers, and cluster changes.

47. What is Kubernetes reconciliation?

Desired state: 3 replicas Actual state: 2 replicas ↓ Controller observes: Desired != Actual ↓ Create Pod ↓ Desired = Actual

This reconciliation loop is fundamental to Kubernetes.

48. One Pod is receiving all traffic. Why?

Possible causes include Service endpoint issues, readiness configuration, session affinity, application connection behavior, load-balancing behavior, service mesh configuration, EndpointSlice state, or only one Pod actually being Ready.

kubectl get endpoints
kubectl get endpointslice
kubectl get pods -o wide

Verify that all intended Pods are Ready and represented in the Service endpoints.

49. Node suddenly becomes NotReady. What do you do?

Step 1 — Confirm

kubectl get nodes
kubectl describe node <node>

Step 2 — Check node conditions

  • MemoryPressure
  • DiskPressure
  • PIDPressure
  • NetworkUnavailable

Step 3 — Check workloads

kubectl get pods -A -o wide

Step 4 — Check EKS infrastructure

  • EC2 status
  • Auto Scaling Group
  • Instance health
  • EBS
  • Network
  • IAM
  • CNI
  • kubelet/container runtime

Step 5 — Recover

Depending on the cause, replace the unhealthy node, allow workloads to reschedule, and validate application health. A senior engineer should focus on service availability first, then root cause.

Mock Interview Scenario — Production EKS Returns HTTP 503

Scenario

Internet ↓ Route 53 ↓ ALB ↓ Ingress ↓ Kubernetes Service ↓ Pods ↓ RDS

Users suddenly receive HTTP 503. Kubernetes shows:

Pod 1   Running
Pod 2   Running
Pod 3   Running

Interview-ready answer

If users are getting 503 while the Pods are showing Running, I would not assume the Pods are healthy. Running only means the containers are running; they may not be Ready or reachable. I would troubleshoot from the outside in.

1. Check the ALB

Check ALB target health and metrics:

  • Are targets healthy?
  • Are they returning 5xx?
  • Is the ALB unable to connect to targets?
  • What is target response time?

If the ALB has no healthy targets, that can directly explain the 503.

2. Check the Ingress

kubectl get ingress -A
kubectl describe ingress <ingress-name>

Verify hostname, Service name, Service port, target port, and AWS Load Balancer Controller events/errors.

3. Check the Service

kubectl get svc
kubectl describe svc <service-name>
kubectl get endpoints <service-name>
kubectl get endpointslice

If the Service has no endpoints, it has no healthy Pods behind it.

4. Check Pod readiness

kubectl get pods
kubectl describe pod <pod-name>

Check READY, STATUS, and RESTARTS.

NAME READY STATUS app-1 0/1 Running app-2 0/1 Running app-3 0/1 Running

The Pods are technically running, but none are Ready. Investigate the readiness probe.

5. Check the readiness probe

readinessProbe:
  httpGet:
    path: /health
    port: 8080

Verify the health endpoint, port, startup time, and whether dependencies such as RDS are causing readiness to fail.

6. Check the Service selector

For example, a Service might select:

selector:
  app: payment

while Pods have:

labels:
  app: payments

This produces no matching Pods and therefore no endpoints.

kubectl get svc <service> -o yaml
kubectl get pods --show-labels

7. Check Pod logs

kubectl logs <pod>
kubectl logs <pod> --previous

Look for startup errors, database failures, port binding errors, configuration problems, authentication failures, and dependency failures.

8. Test the application from inside Kubernetes

Bypass the ALB and test the Service directly.

kubectl run test --rm -it \
  --image=curlimages/curl -- sh

curl http://<service-name>:<port>/health

This helps determine whether the failure is at the ALB/Ingress layer or the Service/Pod/Application layer.

9. Check AWS networking

If the application works internally but ALB still reports unhealthy targets, check:

  • Security Groups
  • Network ACLs
  • Route tables
  • ALB-to-target connectivity
  • Target port
  • AWS Load Balancer Controller
  • AWS VPC CNI health

10. Check RDS after isolating the application layer

Pod ↓ DNS ↓ Network ↓ Security Group ↓ RDS

Check DNS resolution, port 3306 connectivity, security groups, credentials, connection pool, RDS CPU/connections/storage, and database availability.

Best interview answer

"I would isolate the failure domain from ALB to Ingress to Service to endpoints to Pod readiness and finally the application and its dependencies, rather than assuming that a Running Pod is a healthy Pod."
