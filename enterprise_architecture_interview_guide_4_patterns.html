How to Explain Any Architecture in an Interview

Do not start by listing AWS services.
Start with the business requirement, then explain how each architectural layer solves that requirement.
1. Business problemWhat were you trying to achieve?
2. Entry / accessHow do users or systems reach the application?
3. Application flowHow does a request move through the platform?
4. DataWhere is data stored and how is it accessed?
5. SecurityIdentity, authorization, network, secrets and encryption.
6. DeploymentHow are infrastructure and applications released?
7. ResilienceHow do you handle failure and scale?
8. Your roleWhat did you personally design, implement or decide?

Pattern 1 — myPKFiT: Enterprise IaC + EC2 + Internal ALB

Architecture objective: Standardize AWS infrastructure provisioning for an enterprise EC2 application while enforcing secure credentials, approved operating-system baselines, private network access and reusable infrastructure patterns.

IaCTerraform + Takeda private Terraform Cloud modules
CredentialsVault issues temporary STS credentials
ComputeEC2 instances using approved RHEL8 Golden AMIs
TrafficInternal ALB with host-header routing
RoutingSeparate target groups for pkc3, pkc2, mma2 and vdz1
HealthHTTP /index.html health checks

Pattern 1 — Enterprise Architecture Diagram

Pattern 1 — Interview Story

60–90 seconds:
“I worked on the myPKFiT infrastructure architecture using Terraform. The main objective was to provision AWS infrastructure consistently using Takeda’s enterprise standards and reusable private Terraform Cloud modules. Terraform state was maintained remotely in Terraform Cloud, while AWS authentication was integrated with Vault so Terraform received temporary STS credentials rather than using static AWS access keys.

For the application layer, we provisioned EC2 instances for components such as pkc3, pkc2, mma2 and vdz1. The instances used approved RHEL8 Golden AMIs selected dynamically from a shared AWS account. This gave us a controlled and consistent operating-system baseline.

Traffic was handled by an internal Application Load Balancer. Host-header listener rules routed requests to separate target groups for each application component. The ALB used HTTP health checks against /index.html so unhealthy instances were removed from traffic.

The architecture was also modular. Environment-specific configuration was separated from reusable modules for EC2, ALB, RDS, S3, IAM and other infrastructure. The main benefits were standardization, security, reusability and controlled private access.”

What you should emphasize

  • Security: Vault + temporary STS credentials, no static AWS keys.
  • Enterprise standardization: private modules and approved Golden AMIs.
  • Networking: internal ALB rather than direct internet exposure.
  • Scalability of the design: separate target groups and reusable modules.
  • Operations: ALB health checks and centralized Terraform state.

Pattern 1 — Likely Interview Questions

QuestionStrong answer direction
Why Terraform Cloud?Centralized remote state, controlled execution, reusable private modules and enterprise governance.
Why Vault?Avoid long-lived AWS access keys; obtain short-lived STS credentials for Terraform.
Why Golden AMI?Approved, hardened and consistent OS baseline across enterprise workloads.
Why internal ALB?The application is intended for private enterprise access, reducing public attack surface.
Why host-based routing?Multiple application components can share one ALB while routing to separate target groups.
Why separate target groups?Independent health checks, routing, scaling and operational isolation.
What happens when EC2 is unhealthy?ALB health checks fail and the instance is removed from the traffic rotation.

Pattern 2 — OneSourceQA: Private Serverless API + Data Platform

Architecture objective: Build a private enterprise application with SSO/MFA, fine-grained authorization, private frontend hosting, API-driven services, private data connectivity and secure automated deployment.

IdentityMicrosoft Entra ID, Enterprise SSO, MFA, OAuth/OIDC
EdgeRoute 53, WAF and CloudFront
FrontendPrivate S3 React application, OAC and KMS
APIRegional API Gateway with explicit E01–E26 routes
AuthorizationLambda REQUEST Authorizer + JWT/JWKS + user/role/center checks
DataLambda to Databricks through Site-to-Site VPN; Lakebase / ODS

Pattern 2 — Enterprise Architecture Diagram

Pattern 2 — Interview Story

2 minutes:
“OneSourceQA is a private enterprise application running in AWS. The main design goals were private-by-default access, enterprise SSO and MFA, fine-grained authorization, private data connectivity and automated secure deployment.

Users access the application through the Takeda internal application portal and Microsoft Entra ID. Private DNS is used for the application endpoint. The request enters through WAF and CloudFront. CloudFront serves the React frontend from a private S3 bucket using Origin Access Control and KMS encryption.

API traffic is forwarded to a Regional API Gateway. Instead of using a generic catch-all route, the API uses explicit E01 through E26 routes. Before the business Lambda executes, API Gateway invokes a Lambda REQUEST Authorizer. The authorizer validates the Entra JWT and performs application-specific user, role and center authorization.

Once authorized, the request is routed to the appropriate Lambda service running in private networking. The services use private container images from ECR and communicate with the data platform through a Site-to-Site VPN. The platform includes Databricks, Lakebase and ODS data. Reporting is separated into a dedicated Reports Lambda.

From the DevOps side, GitHub Actions handles build, test, security checks and deployment. GitHub uses OIDC federation to obtain AWS access instead of storing long-lived AWS credentials.”

Architectural principles

  • Private-by-default application access.
  • Enterprise identity separated from application authorization.
  • Explicit API routing instead of a generic proxy.
  • Independent Lambda services for scaling and failure isolation.
  • Private connectivity to the data platform.
  • OIDC-based CI/CD authentication.

Pattern 2 — Likely Interview Questions

QuestionStrong answer direction
Why Lambda Authorizer?Authorization required application-specific user, role and center checks in addition to JWT validation.
Why explicit API routes?Better routing, authorization, observability and service ownership than a generic catch-all.
Why private S3?Prevent direct public bucket access; CloudFront accesses the bucket through OAC.
Why CloudFront?Edge delivery, SPA routing and a controlled entry point in front of private origins.
Why Site-to-Site VPN?Private connectivity between AWS workloads and the external data platform.
How is CI/CD secured?GitHub Actions uses OIDC federation and IAM rather than long-lived AWS keys.
How do you protect secrets?Use managed secret storage such as Secrets Manager and least-privilege IAM.

Pattern 3 — Enterprise Architecture Diagram

Pattern 3 — Interview Story

90 seconds:
“Another architecture I worked with was a Spring Cloud microservices platform running on Amazon EKS. The main objective was to move the application into a cloud-native Kubernetes architecture where individual services could be deployed and scaled independently.

At the entry point, an AWS Application Load Balancer was integrated through Kubernetes Ingress. The ALB handled TLS and routed requests to the appropriate Kubernetes service.

The application consisted of separate Spring Boot services such as vdz-app and vdz-calculator. We also had Spring Cloud platform services: Eureka for service discovery and Config Server for centralized configuration. The services were deployed as Kubernetes workloads and packaged using Helm charts.

For scalability, we used Kubernetes HPA so workloads could scale horizontally based on demand. For persistence, the application used AWS RDS MySQL. Persistent storage was handled through the configured EFS/PVC approach where required.

Container images were built with Maven and OpenJDK 11 and stored in Takeda’s private JFrog Artifactory. Harness was used for CI/CD and Helm-based deployment. Security included TLS at the ingress layer, Kubernetes RBAC and image pull secrets.

The key architectural benefits were independent service deployment, Kubernetes-based scaling, centralized configuration, service discovery and clear separation between business services, platform services and the data layer.”

Important interview nuance: Eureka vs Kubernetes Service Discovery

Be ready for this question: “Why did you use Eureka when Kubernetes already provides service discovery?”

A safe answer is: “Kubernetes provides native service discovery through Kubernetes Services and DNS. In this architecture, Eureka was part of the existing Spring Cloud application platform and provided application-level service registration/discovery. If I were redesigning the platform today, I would evaluate whether Eureka is still necessary and whether Kubernetes-native discovery would simplify the architecture.”

Why Helm?Reusable Kubernetes templates, environment-specific values and repeatable releases.
Why HPA?Automatically adjust pod replica count based on workload demand/metrics.

Pattern 4 — Global E-Commerce on EKS with Database & Disaster Recovery

Architecture objective: Build a globally scalable e-commerce platform on Amazon EKS with multi-AZ high availability, multi-Region disaster recovery, resilient transactional data, globally distributed cart/session data, asynchronous event processing and controlled Regional failover.

Global trafficRoute 53 + AWS Global Accelerator for health-aware Regional routing
Edge securityCloudFront + AWS WAF + Shield
ComputeMulti-AZ EKS clusters in primary and DR Regions
Transactional databaseAurora Global Database for orders/customer data where the consistency model fits
Global stateDynamoDB Global Tables for suitable cart/preferences/session workloads
CacheElastiCache Redis for low-latency temporary data
EventsAmazon MSK/Kafka for asynchronous order, payment and inventory events
Object dataS3 with versioning and Cross-Region Replication
DRWarm/active Regional stack, automated traffic failover and tested runbooks
Architect-level principle: Do not force every workload into one database or make every database active-active. The data strategy should follow transactionality, consistency, latency, replication characteristics and the business RPO/RTO.

Global E-Commerce — Database & Disaster Recovery Architecture

Global E-Commerce — Interview Explanation

2–3 minute architect answer:
“For a global e-commerce application, I would design the platform as a multi-Region and multi-AZ EKS architecture. The important point is that the application tier and data tier have different availability and consistency requirements, so I would design them separately.

At the global entry point, Route 53 and AWS Global Accelerator can provide health-aware traffic routing to Regional endpoints. CloudFront would cache static product content and AWS WAF would provide application-layer protection. Each Region would have its own VPC spanning multiple Availability Zones, with an ALB in the public subnets and EKS workloads running in private subnets.

The EKS platform would contain independently deployable services such as catalog, customer, cart, order, inventory, payment and notification. HPA would scale pods, while Karpenter or Cluster Autoscaler would scale the underlying nodes. Pods would be distributed across Availability Zones, with readiness probes, disruption budgets and appropriate topology rules.

The database strategy is workload-specific. For transactional workloads such as orders and customer data, Aurora Global Database is a strong option when the application's consistency model fits a primary-writer architecture. The secondary Region can be promoted during a Regional disaster. For highly distributed workloads such as shopping carts or preferences, DynamoDB Global Tables can be considered because it supports multi-Region reads and writes, but I would explicitly evaluate its consistency and conflict model before choosing it.

S3 would be used for product images and documents with versioning and Cross-Region Replication. Redis would provide low-latency caching, and MSK/Kafka would decouple order, payment, inventory and notification workflows through asynchronous events.

For disaster recovery, both Regions would be provisioned through Infrastructure as Code and kept deployment-compatible. Container images would be available in the recovery Region, secrets and configuration would have an appropriate recovery strategy, and the database replication path would be continuously monitored. During a Regional failure, global traffic would move to the healthy Region, the transactional database would be promoted according to the DR runbook, and critical flows such as checkout, inventory and payment would be validated.

Finally, I would define RPO and RTO with the business before claiming the architecture meets a DR target. We would regularly test Regional failure, database promotion, traffic failover and failback.”

Global E-Commerce — Interview Questions

QuestionStrong answer direction
Did you consider the database?Yes. Database architecture is a first-class part of the design. Separate transactional, globally distributed, cache and object-storage workloads.
Why Aurora Global Database?Strong candidate for transactional relational workloads requiring ACID semantics and cross-Region recovery.
Why not use DynamoDB for everything?Different workloads have different transaction and consistency requirements. Use DynamoDB where its access model and consistency characteristics fit.
Can both Regions accept writes?Only where the workload and data model support it. Do not assume active-active writes are safe for orders/inventory.
What happens if the primary Region fails?Health-aware traffic routing sends requests to the recovery Region; promote the transactional database; validate critical application flows.
What is your RPO?It is a business requirement. Quantify it against the actual replication technology and measured replication lag.
What is your RTO?Also a business requirement. It must be validated through DR exercises rather than assumed from the architecture diagram.
How do you prevent duplicate payments?Idempotency keys, durable payment state and safe retry handling.
How do you prevent inventory overselling?Atomic/conditional reservation logic, concurrency control and an explicit inventory reservation model.
Why Kafka/MSK?Decouple services and process order/payment/inventory/notification events asynchronously.
How do you protect the EKS platform?Private subnets, IAM least privilege, Pod Identity/IRSA, RBAC, NetworkPolicy, WAF, image scanning, secrets management and centralized audit.
How do you test DR?Regular Regional failure drills, database promotion tests, traffic failover, dependency validation and documented failback runbooks.

Critical interview distinction

Do not say: “The entire architecture is active-active, so there is zero data loss.”

Say: “The application tier can be active-active across Regions, but database write patterns are workload-specific. For transactional data I would use a controlled primary/secondary model unless the business and database consistency model justify active-active writes.”

How to choose between them

  • EC2: Good when the application/runtime is VM-oriented or needs OS-level control.
  • Lambda: Good for event/API-driven workloads where managed serverless execution reduces operational overhead.
  • EKS: Good when you need Kubernetes orchestration, multiple containerized services, platform control and portability.

Strong Architect-Level Closing

“When I look at these architectures, I don't start with the AWS services. I start with the application requirements and operational constraints. For the EC2 pattern, the priorities were standardized infrastructure, approved AMIs, secure credentials and private load balancing. For OneSourceQA, the priorities were private-by-default access, enterprise identity, fine-grained authorization and secure API/data connectivity. For the EKS platform, the priorities were independent microservices, Kubernetes orchestration, service discovery, centralized configuration and horizontal scaling.

My role as an architect is to understand those requirements, select the appropriate platform, define the security and networking boundaries, automate the infrastructure and deployment, and make sure the architecture can operate reliably at scale.”

One sentence to remember

“I choose the architecture based on the business and operational requirements first, and then use the appropriate AWS and platform services to satisfy those requirements securely and at scale.”
