1. Terraform Fundamentals

Q1. What is Terraform and why did you choose it for enterprise infrastructure?

Terraform is an Infrastructure as Code tool that defines infrastructure declaratively. In an enterprise environment, the major benefits are consistency, repeatability, version control, reusable modules, automated change management and the ability to manage infrastructure across multiple AWS accounts and environments.

Q2. Terraform vs CloudFormation — why Terraform?

Terraform provides a common IaC model across multiple providers and has a strong module ecosystem. In an enterprise environment, private reusable Terraform modules and Terraform Cloud can provide centralized state and execution. This supports standardization instead of allowing every team to implement infrastructure differently.

Q4. What is the difference between declarative and imperative infrastructure?

Declarative: describe the desired end state; Terraform determines the actions required to reach it. Imperative: explicitly define the sequence of commands or actions. Terraform's declarative model makes infrastructure repeatable and easier to review.

2. Terraform State, Remote State & Drift

Q5. What is Terraform state?

Terraform state maintains Terraform's understanding of the infrastructure it manages. It maps Terraform resources to real infrastructure and helps Terraform determine what needs to be created, changed or destroyed.

Q6. Why don't you store Terraform state locally?

Local state creates collaboration, security, locking and recovery problems. In an enterprise environment, remote state in Terraform Cloud provides centralized access control, consistent state management and controlled Terraform execution.

Q7. What problems can happen with Terraform state?

  • State corruption
  • Concurrent modifications
  • Sensitive information exposure
  • State drift
  • Manual state changes
  • Incorrect resource mapping
  • Accidental resource deletion

Q8. What is state locking?

State locking prevents multiple Terraform operations from modifying the same state concurrently. This protects against race conditions and state corruption.

Q9. What is infrastructure drift?

Terraform says: EC2 = t3.large
                 |
                 | someone changes AWS manually
                 v
AWS actually:    EC2 = t3.xlarge
Terraform detects differences during terraform plan. The desired configuration, state and real infrastructure are reconciled through the plan.

Q10. How do you handle drift?

First identify why the drift occurred. If the manual change is not intended, Terraform should reconcile it. If the change is legitimate, update the Terraform configuration so the source of truth remains the code rather than the console.

Q11. What is terraform import?

terraform import aws_instance.app i-1234567890
Import brings an existing resource into Terraform state. It does not automatically create the correct Terraform configuration, so configuration must be written and validated afterward.

“We used Terraform Cloud to provide centralized remote state management and controlled Terraform execution. We also leveraged Takeda's private modules and enterprise governance. This gave us a standardized IaC model rather than allowing every team to implement AWS infrastructure independently.”

Q14. How would you manage DEV, TEST, UAT and PROD?

Use clear environment isolation, usually with separate Terraform Cloud workspaces or projects and separate state. Keep reusable logic in modules and environment-specific values outside the module implementation.

Q15. How do you handle concurrent production changes?

Use remote state locking/controlled runs, code review, plan review, policy checks and approval gates. The goal is that production infrastructure changes are serialized and auditable.

4. Terraform Modules

Q17. Why use private enterprise modules?

Private modules enforce enterprise standards. Instead of every team designing EC2, ALB, IAM or networking differently, an approved module provides a controlled implementation that teams consume through inputs and outputs.

Q18. What should be inside a reusable module?

modules/ec2/
├── main.tf

Q19. What should not be hardcoded?

Avoid hardcoding AMI IDs, Regions, environments, account IDs, VPC IDs, subnet IDs and application names. Pass them as variables or derive them through data sources.

Q20. How do you version modules?

Use Git tags or an enterprise module registry. Applications should consume an explicit tested module version instead of automatically taking untested changes.

“We did not hardcode AWS access keys. Terraform integrated with Vault to obtain temporary STS credentials. This reduces the risk associated with long-lived credentials.”

Q22. Why are temporary STS credentials better?

They are short-lived and reduce the exposure window if credentials are compromised. They also support stronger enterprise credential management than static access keys.

Q23. Would you store AWS credentials in Terraform variables?

No. Prefer IAM roles, OIDC, STS, Vault or supported dynamic credentials mechanisms. Never commit long-lived AWS access keys to Terraform code.

Q24. How do you manage secrets in Terraform?

Use services such as AWS Secrets Manager or Vault. Be careful: secret values can still enter Terraform state depending on how they are consumed. Avoid unnecessarily passing secret values through Terraform and prefer runtime retrieval where possible.

Q25. How do you implement least privilege?

Give the Terraform execution identity only the permissions required for the infrastructure it manages. Separate roles by environment and use explicit IAM policies rather than broad administrator permissions where practical.

6. Lifecycle, Dependencies & Data Sources

Q26. What is create_before_destroy?

lifecycle {
  create_before_destroy = true
}
It tells Terraform to create a replacement resource before destroying the old one when the resource supports that lifecycle behavior. It can help reduce downtime during replacement.

Q27. What is prevent_destroy?

lifecycle {
  prevent_destroy = true
}
It prevents Terraform from destroying a protected resource through normal Terraform operations. It is useful for critical resources but should be used thoughtfully.

Q28. What is ignore_changes?

It tells Terraform to ignore changes to selected resource attributes. It can be useful when an external system legitimately manages an attribute, but excessive use can hide real drift.

Q29. How does Terraform know resource dependencies?

subnet_id = aws_subnet.private.id
Terraform builds a dependency graph from resource references. In this example, the EC2 resource depends on the subnet resource.

Q30. What is depends_on?

An explicit dependency used when Terraform cannot infer a dependency automatically. Use it only when a real dependency exists.

Q31. What is a data source?

A data source queries existing information rather than creating it. In your Golden AMI example, Terraform can query an approved RHEL8 AMI and pass the selected ID into the EC2 module.

Q33. Should terraform apply run automatically on every commit?

Not necessarily. Automatic apply can be appropriate for lower environments. For production, I prefer controlled approval, policy checks, clear separation of duties and auditable execution.

Q35. How do you make Terraform CI/CD secure?

  • Use OIDC/STS or Vault instead of long-lived keys.
  • Run validation and security checks before apply.
  • Use protected branches and required reviewers.
  • Separate non-production and production roles.
  • Restrict who can execute production applies.
  • Keep state remote and access controlled.

8. Enterprise Governance & Security

Q36. How do you prevent teams from creating insecure infrastructure?

Use private approved modules, policy-as-code, CI/CD checks, code review, security scanning, TFLint, mandatory tagging and controlled Terraform Cloud execution.

Q37. What Terraform security tools do you know?

Q38. What does TFLint do?

TFLint is primarily a Terraform linter. It detects potential errors, provider-specific issues, deprecated syntax and configuration problems before infrastructure is deployed. It is not a complete security solution by itself.

Q39. How would you enforce mandatory tags?

Use reusable modules, AWS provider default tags where appropriate, CI validation and policy-as-code. Typical enterprise tags include Application, Environment, Owner, CostCenter, APMSID, RecoveryTier and Compliance.

Q40. A developer wants an internet-facing ALB but policy requires internal ALBs. What do you do?

Enforce the requirement with policy-as-code rather than relying only on documentation. The Terraform plan should fail if the ALB violates the enterprise policy.

9. Advanced Architect Scenarios

Q41. What happens if Terraform apply fails halfway through?

Terraform records successfully created resources in state and reports the failure. After correcting the issue, another plan/apply can reconcile the infrastructure to the desired state. Investigate the failure before blindly rerunning.

Q42. Someone manually deletes an EC2 instance. What happens?

Run terraform plan. Terraform sees that the desired resource is missing and normally proposes recreating it.

Q43. How do you handle provider upgrades?

Use explicit provider version constraints, test upgrades in lower environments, review the plan for breaking changes and promote the tested version to production.
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
}

Q44. What is the difference between exact version and ~>?

An exact version pins a specific version. A pessimistic constraint such as ~> 6.0 allows compatible releases within the defined constraint rather than taking arbitrary major-version changes.

Q45. You have 100 AWS accounts. How would you manage Terraform?

Use centralized Terraform Cloud organization/project/workspace structure, separate state per environment/account, reusable modules, controlled IAM roles, OIDC/STS or Vault, policy-as-code, tagging standards and clear ownership.

Q48. Why did you use a private Terraform module for EC2?

To standardize EC2 provisioning across the enterprise, including approved AMIs, tagging, security controls and reusable implementation patterns.

Q49. How did you dynamically select the Golden AMI?

Use a Terraform data source to query the approved RHEL8 AMIs in the shared AWS account, select the appropriate image based on the required filters, and pass that AMI ID to the private EC2 module.

Q50. How did Terraform create the ALB architecture?

Terraform
   |
   +-- Internal ALB
   |
   +-- Listener :80
   |
   +-- Host-header Rules
   |
   +-- Target Groups
   |

   |
   +-- EC2 Targets
   |

Q51. Why host-based routing?

Multiple application components can share one ALB while still routing different hostnames to separate target groups. This reduces duplicated infrastructure while keeping application routing logically separated.

Q52. Why separate target groups?

Each application component can have independent routing, health checks, registration, scaling and operational isolation.

Q53. Why an internal ALB?

The application is intended for private enterprise access rather than direct public Internet exposure. The internal ALB reduces the public attack surface while still providing Layer 7 routing inside the enterprise network path.

Q54. Why Golden AMIs?

Golden AMIs provide an approved, standardized and controlled RHEL8 operating-system baseline that can include required patches, hardening and enterprise agents.
